# Algorithms and Computation

- [Algorithms and Computation](https://youtu.be/ZA-tUyM_y7s?si=4rsbA4wycsTIUaQh)

---

Algorithm이라고 하면 그냥 문제를 빨리 푸는 방법이라고 생각했는데, 강의에서는 Correctness과 Efficiency를 설명할 수 있어야 한다고 합니다.

우리가 일반적인 애플리케이션 개발을 하게 되면, XUnit같은 테스트 프레임워크를 사용해서 테스트 코드로 여러 입력을 넣어보고 예상한 값과 결과가 동일한지 확인하죠.

```plaintext
입력A → 성공
입력B → 성공
입력C → 성공
```
그러면 작성된 TC는 잘 통과했으니, 배포하면 됩니다.

근데 강의에선 Algorithm은 여기서 만약 TC에 없는 케이스가 있다면? 입력이 10개가 아니라 100만개라면? 우리가 생각하지 못한 이상한 입력이 들어온다면? 이라는 질문을 계속 던지고 있습니다.

그래서 Algorithm에서는 계속해서 왜?라는 질문을 붙입니다.

```plaintext
왜 이 입력에서 잘 동작하지?
↓
그러면 다른 입력에서도 잘 동작하나?
↓
왜 모든 가능한 입력에서도 잘 동작한다고 말할 수 있지?
```
결국 가능한 모든 입력에 대해 올바르다는 걸 논리적으로 보여주는 것이 중요하다고 합니다.

이게 강의에서 말하는 Algorithm Correctness와 연결됩니다.

## Computational Problem?

컴퓨터로 풀어야 하는 문제 정도로 이해했는데, Algorithm 관점에서는 대략 

```plaintext
입력과 그 입력에 대해 허용되는 올바른 출력 사이의 관계
```

라고 볼 수 있습니다.

뭔 말인지 좀 헷갈리는데, 강의 노트에서는 생일을 예시로 들더라구요.

```json
[
  (김철수, 2월 3일),
  (신짱구, 5월 13일),
  (박맹구, 2월 3일)
]
```
(맹구 성을 모ㄹ라요.....ㅠㅠ)

위 같이 3명의 학생이 있고, 만약 Problem이 학생들의 이름과 생일이 주어졌을 때 생일이 같은 두 학생을 찾으라고 한다면

여기서는 쉽게 철수와 맹구라고 찾을 수 있겠죠. 근데 짱구까지 생일이 똑같이 2월 3일이 된다면

```json
[
  (김철수, 2월 3일),
  (신짱구, 2월 3일),
  (박맹구, 2월 3일)
]
```

이제 정답은 하나가 아니라

김철수 - 신짱구
김철수 - 박맹구
신짱구 - 박맹구

이렇게 세 개 모두 올바른 답이라고 할 수 있습니다.

여기서 중요한 포인트가 나오는데, 왜 Problem을 함수가 아니라 관계라고 하는걸까요?

제가 가장 헷갈리고 지금도 조금 이해가 안가는 부분이기도 합니다.

보통 프로그래밍에서 함수를 생각하면 이런 모습입니다.

```plaintext
정의) 입력 → 출력
예) f(2) = 4
```

위 처럼 하나의 입력이 하나의 출력에 대응됩니다. 

그런데 앞서 생일 문제는 조금 다른데, 하나의 입력에 대해 가능한 정답이 여러개 존재할 수 있다는 거죠.

```plaintext
입력
↓
{
  김철수 - 신짱구,
  김철수 - 박맹구,
  신짱구 - 박맹구
}
```

즉 Problem은 입력이 곧 정답 하나를 의미하는 1대1 대응관계가 아니라, 

```plaintext
입력 → 허용되는 정답들의 집합
```

이라고 이해하면 좀 쉽게 이해되는 것 같습니다.

그래서 함수라기보다 입력과 출력 사이의 관계라고 표현하는 겁니다.

Problem은 반드시 이것을 반환하라고 말하는게 아니라, 이 조건을 만족하는 결과라면 정답으로 인정한다를 정의하는 거죠.

오묘한 차이라고 느껴지는데, 쓰다 보니 이해가 되는..건가? 되는 것 같습니다,,,?

---

여기서 또 구분을 하는데, Problem과 Algorithm은 다르다라고 언급합니다.

사실 이건 크게 어렵지 않을거에요. Problem은 무엇을 해결해야 하는가?를 정의하는거고 생일 문제라면 다음 문장 자체가 Problem 일겁니다.

```plaintext
학생들의 이름과 생일이 주어졌을 때 생일이 같은 두 학생을 찾아라
```

여기서는 어떻게 찾을지에 대해서는 전혀 이야기하지 않았죠.

재귀를 사용할 수도 있고, 뭐 내림차순 정렬을 쓸 수도 있고, Linked List 사용할 수도 있습니다.

앞서 말했 듯이 Problem은 조건에 맞는 답만 나오면 됩니다.

그러니 결국 Algorithm이 의미하는 건 Problem을 실제로 해결하기 위한 구체적인 해결책이라고 볼 수 있겠네요.

생일 문제를 해결한다고 하면

```plaintext
첫 번째 학생을 확인한다.

다음 학생을 확인한다.

현재 학생의 생일을
앞에서 확인한 모든 학생의 생일과 비교한다.

같은 생일이 있으면 두 사람을 반환한다.

없으면 다음 학생으로 넘어간다.
```

이건 하나의 Algorithm이고, 다르게 풀 수도 있습니다.

학생을 생일순으로 정렬하고 맨 뒤부터 두 명만 비교할 수도 있겠죠. 결국 하나의 Problem을 해결하는 Algorithm은 여러 개 존재할 수 있다는 겁니다.

---

근데 왜 한 번 정답을 냈다고 Correct한 Algorithm일까요?

어떤 Algorithm을 실행했더니 정답이 나왔습니다. 그럼 이 Algorithm이 올바른 걸까요?

사실 Algorithm 관점에서는 아직 부족하다고 할 수 있습니다.

우리가 확인한건 이 입력에서는 잘된다뿐이지 Algorithm에서는 모든 유효한 입력에서도 잘 된다를 보여줘야 하기 때문이죠.

그래서 Correctness Proof가 등장합니다.

생일 문제를 다시 생각해보겠습니다.

우리가 만든 Algorithm은 새로운 학생을 한 명 볼 때마다 이전 학생들과 비교합니다. 그리고 같은 생일을 발견하면 반환합니다.

직관적으로는 잘 동작할 것 같지만, Algorithm은 여기서 멈추지 않고 정말 빠뜨리는 경우가 없는지를 검사해야 하는데 이때 자주 사용하는게 수학적 귀납법이라고 합니다.

생각해보면 Algorithm의 반복문과 귀납법은 꽤 비슷한 구조를 가지고 있습니다.

```plaintext
처음에는 올바르게 동작한다.
↓
k번째까지 올바르게 동작한다고 가정한다.
↓
k+1번째에서도 올바르게 동작함을 보인다.
↓
따라서 모든 경우에서 올바르게 동작한다.
```
그래서 반복문이나 재귀 Algorithm의 Crrectness를 증명할 때 귀납법이 쓰인다고 합니다.

근데 맞는 Algorithm이라고 끝도 아닌게, 다음의 Algorithm이 있다고 가정하면

```plaintext
학생 10명 → 0.001초
학생 1,000명 → 1초
학생 1,000,000명 → 몇 시간
```
결과는 항상 정확하긴 한데, 입력이 조금만 커지면 사용할 수 없을 정도로 느려집니다.

결국 좋은 Algorithm은 아니라는거죠. 이게 Algorithm을 공부하는 본질적인 이유이기도 하구요.

그래서 Correctness 다음으로 **Efficiency**를 생각해야 합니다.

## Efficiency

Efficiency는 입력이 커질 때 얼마나 느려지느냐인데, Algorithm 속도를 측정할 땐 보통 실행 환경까지 고려를 합니다.

그래서 Algorithm에서 보통 실제 시간을 재기보다는

```plaintext
입력 크기가 증가할수록 필요한 연산 횟수가 어떻게 증가하는가?
```

를 분석합니다.

입력의 크기를 n이라고 하면, n이 커질수록 실행 시간이 어떻게 증가하는가라고 할 수 있겠죠.

여기서 그 유명한 Big-O가 등장합니다. 예를 들어 실행에 필요한 연산 수가

```plaintext
3n^2 + 5n + 100
```

이라고 해보겠습니다.

n이 작을 때는 모든 항이 어느 정도 영향을 줍니다. 근데 n이 엄청 커지면 n^2이 압도적으로 영향력이 커지죠.

그래서 이 Algorithm의 성장 속도를 대략 `O(n^2)`라고 표현합니다.

결국 핵심은 입력 크기에 따른 비용 증가 속도를 본다고 할 수 있겠네요.

이 뒤에 강의에서 `O(n)`과 `O(n^2)`의 차이에 대해서도 설명한게 있는데, 이건 생략하겠습니다. 

요약하면 작은 테스트는 비슷한데 규모가 커질수록 Algorithm 선택이 굉장히 중요해진다 뭐 그런 내용이었습니다.

## Data Structure

결국 최적의 Algorithm을 찾으려면 Data Structure는 필연적입니다.

```plaintext
첫 번째 학생 → 0번 비교
두 번째 학생 → 1번 비교
세 번째 학생 → 2번 비교
... n번째 학생 → n-1번 비교
```

이 생일 문제에서 총 비교 횟수는 대략

```plaintext
1 + 2 + 3 + ... + (n-1)
```

이 되니 결과적으로 약 O(n^2)이 됩니다.

근데 더 빨리 찾으려면 Hash Table같은 Data Structure가 등장하겠죠.

이미 확인한 생일을 Hash Table에 넣으면 매번 이전 학생을  순회하지 않고, 이 생일이 존재하는지 여부만 빠르게 확인이 가능합니다.

결국 Algorithm 성능은 데이터를 어떤 Data Structure에 저장하느냐도 큰 영향을 받습니다.
