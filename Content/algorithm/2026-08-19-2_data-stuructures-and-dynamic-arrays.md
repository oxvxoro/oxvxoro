예를 들면

```plaintext
i번째 원소 가져오기

맨 앞에 삽입하기
맨 뒤에 삽입하기

```

같은 요구사항을 말합니다.

결국

```plaintext
Interface == 문제/요구사항
Data Structure == 그 문제를 해결하는 구현 방법
```

이라고 할 수 있겠네요.

같은 Interface라도 Array, Linked List, Dynamic Array 같은 다양한 Data Structure로 구현할 수 있고, 어떤 연산이 빠른지는 선택한 Data Structure에 따라 달라집니다.

이 구분이 알고리즘에서 꽤 중요한데, 예를 들어

```plaintext
음식을 보관하고 싶다
```

가 요구사항이라면

```plaintext
냉장고
냉동고
락앤락 밀폐용기
보온병
```

중 무엇을 사용할지는 목적에 따라 달라지는 것과 비슷하다고 볼 수 있죠.

여기서 Interface는 크게 두 가지로 나뉘는데, `Sequence`와 `Set`입니다.

## Sequence

Sequence는 순서가 중요한 자료의 모음입니다.

예를 들어

```json
[5, 2, 9, 7]
```

이라면

```plaintext
0번째 == 5
1번째 == 2
2번째 == 9
3번째 == 7
```

처럼 값뿐만 아니라 위치 자체가 의미를 가집니다.

그래서 다음과 같은 연산이 필요합니다.

```python
get_at(i)
set_at(i, x)

insert_at(i, x)
delete_at(i)

insert_first(x)
delete_first()

insert_last(x)
delete_last()
```

원래 C#만 하다가 알고리즘 공부하려고 Python도 기본 문법만 공부 중인데, 확실히 이런 알고리즘 표현할 때는 이해하기도 쉽고 편하네요ㅎㅎ

다음은 `Set`입니다.

## Set

Set은 위치보다는 key가 무엇인지가 중요합니다.

예를 들어 학생 데이터를 저장한다고 하면

```plaintext
학번 → 학생정보
```

처럼 key를 기준으로 데이터를 찾습니다.

여기서는 학번이 key가 되겠네요.

그래서

```python
find(key)
insert(x)
delete(x)

find_min()
find_max()
find_next()
find_prev()
```

같은 연산이 중요하다고 합니다.

이번에 본 강의 주제는 이 중에서도 Sequence를 어떻게 구현할 것인가입니다.

## Static Array

가장 먼저 나오는 건 Static Array입니다.

예를 들어 메모리에

```plaintext
주소
100   101   102   103
 ↓     ↓     ↓     ↓
[10]  [20]  [30]  [40]
```

처럼 데이터가 연속적으로 저장되어 있다고 생각하면 됩니다.

그래서 만약 2번째 원소를 찾고 싶다면 처음부터 하나씩 볼 필요가 없습니다.

```plaintext
시작 주소 + i
```

를 계산하면 바로 원하는 위치를 찾을 수 있으니까요.

따라서

```python
a[i]

get_at(i) → Θ(1)
set_at(i) → Θ(1)
```

같은 접근은 `Θ(1)`, 즉 상수 시간에 가능합니다.

데이터가 100개든 1만 개든 주소를 계산해서 바로 이동할 수 있기 때문이죠.

물론 단점도 있습니다.

삽입이나 삭제가 일어나면 기존 데이터를 한 칸씩 옮겨야 한다는 겁니다.

만약 배열의 가장 앞에 5를 넣고 싶다면

```plaintext
[10][20][30][40] → [5][10][20][30][40]
```

가 되어야 하는데, 기존 원소를 전부 한 칸씩 뒤로 옮겨야 합니다.

최악의 경우 `n`개의 데이터를 모두 움직여야 하므로 배열에서 삽입이나 삭제는 일반적으로 `O(n)`이라고 할 수 있습니다.

또 Static Array의 크기가 4칸이라면 갑자기 5번째 데이터를 넣을 공간이 없습니다.

결국 더 큰 배열을 새로 만들고 기존 데이터를 전부 복사해야 하고, 이 작업 역시 `O(n)`입니다.

---

## Linked List

Linked List는 데이터가 메모리에 연속해서 붙어 있을 필요가 없습니다.

각 노드는 대략

```plaintext
[값 | 다음 노드 주소]
```

를 가지고 있습니다.

예를 들면 이런 형태입니다.

```plaintext
[10|•] → [20|•] → [30|•] → [40|null]
```

어차피 `next` pointer가 다음 노드의 위치를 알려주기 때문에 각 노드는 실제 메모리에서 서로 멀리 떨어져 있어도 됩니다.

Array에서 단점이었던 삽입, 삭제 문제도 Linked List에서는 pointer만 적절히 변경해주면 되기 때문에 기존 데이터를 전부 옮길 필요가 없습니다.

물론 그만큼 단점도 명확합니다.

Array라면

```plaintext
주소 + 1000
```

같은 식으로 원하는 위치로 바로 이동할 수 있지만, Linked List에서는

```plaintext
1번째 → 2번째 → 3번째 → ... → 1000번째
```

처럼 앞에서부터 pointer를 따라가야 합니다.

따라서 `get_at(i)`는 최악의 경우 `O(n)`입니다.

정리하면

| 자료구조        | 원하는 위치 접근 | 맨 앞 삽입/삭제 |
| ----------- | --------: | --------: |
| Array       |  **Θ(1)** |      Θ(n) |
| Linked List |      Θ(n) |  **Θ(1)** |

입니다.

그냥 서로 반대되는 특징을 가지고 있다고 봐도 될 것 같네요.

Array는 원하는 위치를 찾는 건 빠른 대신 데이터를 움직이는 게 비싸고, Linked List는 데이터를 움직이지 않아도 되는 대신 원하는 위치까지 찾아가는 게 비쌉니다.

## Dynamic Array

Dynamic Array는 Array의 빠른 접근 성능은 유지하면서, 뒤쪽 삽입을 훨씬 효율적으로 만들기 위한 방법입니다.

Python에서 우리가 흔히 사용하는 `list`가 대표적인 예라고 할 수 있겠네요.

아이디어는 간단한데, 배열이 꽉 찰 때마다 딱 1칸씩 늘리지 말고, 미리 넉넉하게 공간을 확보해두자는 겁니다.

예를 들어 실제 데이터가 4개 있다고 가정하면 Static Array는 딱 4칸만 사용합니다.

```plaintext
[10][20][30][40]
```

Dynamic Array는 더 큰 배열을 만들어 여유 공간을 남겨둡니다.

```plaintext
[10][20][30][40][ ][ ][ ][ ]
```

여기서는

```plaintext
capacity = 8
n = 4
```

인 상태입니다.

그러면 다음 데이터를 추가할 때 새 배열을 만들 필요 없이 그냥 빈칸에 값을 넣으면 되므로 `O(1)`입니다.

하지만 언젠가는 이렇게 늘려두었던 배열도 꽉 차겠죠.

8칸을 모두 사용했다고 가정하면

```plaintext
[10][20][30][40][50][60][70][80]
```

이번에는 1칸이나 4칸 정도만 추가하는 것이 아니라, 아예 더 큰 배열을 새로 만듭니다.

강의에서는 이해하기 쉽게 2배 증가를 예시로 듭니다.

```plaintext
[10][20][30][40][50][60][70][80][ ][ ][ ][ ][ ][ ][ ][ ]
```

이 순간에는 기존 8개 데이터를 새 배열로 복사해야 하므로 `O(n)`의 비용이 듭니다.

하지만 한 번 크게 늘려놓고 나면 그다음 여러 번의 삽입에서는 복사를 하지 않아도 됩니다.

그리고 여기서 **Amortized Analysis**라는 개념이 등장합니다.

---

## Amortized Analysis

Dynamic Array에서 `append`를 하면 대부분의 경우 비용은 `O(1)`로 매우 싸게 끝납니다.

하지만 가끔 배열이 꽉 차면 더 큰 배열을 만들고 기존 원소를 전부 복사해야 하기 때문에 `O(n)`이 걸립니다.

그래서 어떤 한 번의 `append`만 놓고 보면 최악의 경우 `O(n)`입니다.

그런데 여러 번의 `append`를 전체적으로 보면 한 번당 비용을 `O(1)`로 볼 수 있습니다.

강의에서는 이것을 **amortized O(1)** 이라고 부릅니다.

그렇다면 가끔 `O(n)`짜리 연산이 발생하는데도 왜 전체적으로는 `O(1)`이라고 할 수 있을까요?

핵심은 배열의 capacity가 보통 다음과 같이 일정한 비율로 증가하기 때문입니다.

```plaintext
1 → 2 → 4 → 8 → 16 → 32 → ...
```

배열이 꽉 찰 때마다 기존 원소를 복사한다고 하면 지금까지 발생한 복사 비용은 대략

```plaintext
1 + 2 + 4 + 8 + 16 + ...
```

처럼 증가합니다.

그런데 `n`개의 원소를 넣을 때 이 합은 대략 `2n`보다 작습니다.

예를 들어 capacity가 16까지 커졌다면

```plaintext
1 + 2 + 4 + 8 = 15
```

이고, 일반적으로도 이전 capacity들의 합은 마지막 크기와 비슷한 수준으로 제한됩니다.

즉 `n`번의 `append`를 수행하는 동안 발생하는 전체 비용은 `O(n)`입니다.

그러면 연산 하나당 비용은

```plaintext
O(n) / n = O(1)
```

이 됩니다.

따라서 각각의 `append` 중 일부는 비쌀 수 있지만, 여러 번의 연산을 묶어서 보면 한 번당 비용은 일정한 수준으로 제한됩니다.

이처럼 여러 연산의 전체 비용을 계산한 뒤, 이를 전체 연산 횟수에 걸쳐 분산해서 분석하는 방법을 **Amortized Analysis** 라고 합니다.

여기서 중요한 점은 이게 확률적인 평균은 아니라는 겁니다.

```plaintext
운이 좋으면 대부분 빠르다
```

는 의미가 아니라,

```plaintext
여러 연산을 연속해서 수행했을 때
전체 비용 자체가 일정한 범위 안으로 제한된다
```

는 뜻으로 받아들이면 될 것 같습니다.

그래서 Python의 `list.append()` 같은 연산이 효율적인 것이겠네요.

Python의 `list`는 Dynamic Array이므로 강의의 모델을 기준으로 보면

```python
list.append(x)
list.pop()
```

처럼 뒤쪽에서 추가하거나 삭제하는 연산은 amortized `O(1)`입니다.

반대로

```python
a.insert(0, x)
```

처럼 맨 앞에 데이터를 넣으면 기존 데이터를 전부 한 칸씩 옮겨야 하므로 `O(n)`이 될 수 있습니다.

### 그런데 삭제할 땐?

이번에는 데이터가 많이 줄었다고 가정해보겠습니다.

```plaintext
capacity = 16

[10][20][ ][ ][ ][ ][ ][ ][ ][ ][ ][ ][ ][ ][ ][ ]
```

데이터는 2개뿐인데 capacity는 16이라면 메모리가 많이 낭비됩니다.

그래서 어느 순간에는 배열을 다시 줄여야 합니다.

그런데 데이터 하나를 삭제할 때마다 바로 배열의 크기를 줄이면 또 문제가 생깁니다.

예를 들어 특정 경계에서

```plaintext
삭제 → resize
삽입 → resize
삭제 → resize
삽입 → resize
```

같은 상황이 반복된다면 비싼 복사가 계속 발생할 수 있습니다.

강의에서는 이를 thrashing과 비슷한 상황으로 설명합니다.

그래서 배열이 어느 정도 충분히 비었을 때만 크기를 줄이고, 줄인 뒤에도 다시 여유 공간을 남겨둡니다.

예를 들어 사용률이 25% 아래로 내려갔을 때 배열을 줄여서 사용률을 다시 50% 정도로 만드는 식입니다.

```plaintext
capacity = 16
size = 4

↓ resize

capacity = 8
size = 4
```

이렇게 하면 resize 직후에도 여유 공간이 남아 있기 때문에 바로 다시 resize가 발생하지 않습니다.

다음 resize가 일어나기 전까지 충분히 많은 싼 연산이 수행되므로 삭제의 상각 비용 역시 낮게 유지할 수 있다고 합니다.

---

정리하면 대략 다음과 같습니다.

| 연산 | Static Array | Linked List | Dynamic Array |
|---|---:|---:|---:|
| `get_at(i)` | **O(1)** | O(n) | **O(1)** |
| `set_at(i)` | **O(1)** | O(n) | **O(1)** |
| 맨 앞 삽입/삭제 | O(n) | **O(1)** | O(n) |
| 맨 뒤 삽입 | O(n) | O(n)\* | **O(1) amortized** |
| 맨 뒤 삭제 | O(n) | O(n)\* | **O(1) amortized** |
| 중간 삽입/삭제 | O(n) | O(n) | O(n) |

위 표는 강의에서 사용하는 기본 Singly Linked List 구현 기준입니다.

Tail pointer나 Doubly Linked List 같은 추가적인 구조를 사용하면 일부 연산의 성능을 개선할 수 있습니다.

강의에서도 이런 식으로 기존 Data Structure에 추가 정보를 붙여 연산을 개선하는 Data Structure Augmentation에 대해 언급합니다.

아 그리고 강의 초반에 Stack과 Queue에 대한 이야기도 잠깐 나옵니다.

Stack이라는 Data Structure는

```plaintext
push → 맨 뒤에 넣기
pop  → 맨 뒤에서 빼기
```

즉 Sequence의 연산으로 표현하면

```plaintext
insert_last
delete_last
```

만 사용한다고 볼 수 있습니다.

Queue는

```plaintext
enqueue → 뒤에 넣기
dequeue → 앞에서 빼기
```

이므로

```plaintext
insert_last
delete_first
```

를 사용하는 Sequence라고 볼 수 있습니다.

결국 Stack이나 Queue도 완전히 별개의 무언가라기보다는, Sequence라는 Interface에서 특정 연산만 허용해서 사용하는 형태라고 생각하면 이해하기 편한 것 같습니다.
